## 二、五个可加提议详细评估

### 提议①：订阅更新推送（✅ v0.7.8 已实现）

- **作用**：订阅漫画 → 后台定期检查新章节 → 发现更新在订阅会话内推送通知
- **实际实现**：
  1. 数据层：`subscriptions.json`，按会话 `umo` 保存 `{album_id: {title, photo_ids, updated}}`
  2. 后台任务：插件 `initialize()` 启动定时协程，默认 3600 秒检查一次（`subscribe_interval`，0=关闭）；每本之间间隔 2 秒
  3. 命令只保留一个入口 `/jmsub`：
     - `/jmsub <漫画id>` 订阅或更新基线
     - `/jmsub list` 查看当前会话订阅
     - `/jmsub del <漫画id>` 取消订阅
  4. 快照对比使用 `photo_id` 集合，避免章节被删/重排造成误报；只推送通知，不自动下载
  5. 推送：`context.send_message(umo, ...)` 向订阅时的会话发送“《标题》新增 N 章”和章节列表
- **注意点**：QQ 官方机器人平台可能不支持主动推送，失败时只记录日志并在下轮重试；群/私聊按会话 `umo` 独立订阅

### 提议②：代理支持（✅ v0.7.7 已实现）

- **作用**：IP 被地区封锁/限流时，通过 HTTP/SOCKS5 代理访问站点（当前只能靠换域名，无逃生通道）
- **实现思路**：配置 `use_proxy`(bool) + `proxy_url`(str) → 在构建 jmcomic option 时映射到 `client.postman.meta_data.proxies`（库原生支持，cosmos 同款接法：config.py:240-246）。注意 cosmos 的做法是"未配置时显式设空代理以覆盖系统代理"，可借鉴避免环境变量干扰
- **实现状态**：v0.7.7 已落地。`use_proxy=false` 时显式传空 dict 直连；开启且填写 `proxy_url` 时 http/https 都走该代理；支持 `http://host:port`、`socks5://host:port`（SOCKS5 需 PySocks）
- **成本**：最低（一个配置项 + option 构建处几行）
- **注意点**：切换后需重载插件生效；帮助文本注明支持的格式（http://host:port、socks5://host:port）

### 提议③：群白名单（✅ v0.7.8 已实现）

- **作用**：比现有 allow_group 总开关粒度更细——只允许指定群使用
- **实际实现**：配置 `enabled_groups`（逗号分隔群号，空=全部）；`allow_group=false` 时所有群禁用，否则再按白名单过滤；所有命令入口统一调用 `_check_permission()`，私聊不受影响
- **注意点**：QQ 官方机器人事件的群标识字段由平台适配器提供；被拦截时提示“本群不在插件群白名单中”

### 提议④：jms 纯数字可配置按车号搜索（✅ v0.7.8 已实现）

- **作用**：`jms 123456`（纯数字）时可选直返漫画详情，省去用户再打一次 `/jmv`
- **实际实现**：配置 `numeric_search_as_album`（默认关闭）；开启后 `/jms <纯数字>` 直接复用 `/jmv` 的详情展示流程，带页码/排序参数时仍按普通搜索处理
- **注意点**：默认关闭，避免把“123”这类正常搜索词误判为车号

### 提议⑤：收藏夹导出（✅ v0.7.8 已实现，30 秒二次确认）

- **作用**：把账号收藏夹导出为 CSV 文件发送，用于备份/迁移
- **实际实现**：`/jmfav export [文件夹id]`（仅号主，无加密/无密码）→ 第一次输入只提示，30 秒内再次输入相同命令才执行 → 遍历收藏夹生成 `id,author,name` 三列 CSV → 作为文件消息发送，发送后删除临时文件
- **注意点**：大收藏夹分页读取、按 ID 去重；CSV 用 `utf-8-sig`，Windows Excel 可直接打开；不同文件夹的导出命令不能互相确认

### 优先级与组合建议

五项提议在 v0.7.8 已全部落地：

| 顺序 | 事项 | 成本 | 状态 |
|---|---|---|---|
| 1 | ② 代理支持 | 最低 | ✅ v0.7.7 |
| 2 | ③ 群白名单 | 最低 | ✅ v0.7.8 |
| 3 | ④ jms 纯数字可配置 | 低 | ✅ v0.7.8 |
| 4 | ① 订阅更新推送 | 中 | ✅ v0.7.8，仅 `/jmsub` |
| 5 | ⑤ 收藏夹导出 | 中低 | ✅ v0.7.8，30 秒二次确认，无加密 |

- BUG-003（进度推送失效）已在 v0.7.7 修复；v0.7.8 根据 QQ 展示效果移除可见进度条，改为 `/jmnow` 主动查询。

| 5 | `/jmcheckin`、`/jmme`：连续签到 0 天、今日签到 ❌ 未签 | API 客户端的 `get_daily` 响应没有 `oldStep`、`error` 字段（这两个字段属于 HTML 客户端），插件按这两个字段解析，永远得到 0 / 未签 | 客户端接口差异 |

### 二、修复内容（main.py）

1. **下载目录**：显式设置 `dir_rule.rule = Bd/JM{Aid}_{Atitle}/Pname`：
   - 漫画根目录：`downloads/JM{漫画id}_{标题}/`
   - 章节目录：`.../{章节名}/`
   - 目录名带漫画ID，`_find_album_dir()` 可按 ID 精确复用缓存。

2. **目录定位兜底**：`ProgressDownloader.after_image()` 记录图片实际写入的漫画根目录（取 `base_dir` 下第一层目录），`_find_album_dir()` 优先使用该记录；其次按 `JM{id}_*` 前缀匹配。
   新增 `_album_dir_has_images()`，查找时校验目录内确有图片，避免把空目录/半成品当成已下载。

3. **批量下载**：目录查找失败时单独提示"下载后仍找不到目录"；ZIP 名与历史记录标题去掉 `JM{id}_` 前缀。

4. **评论超页**：拿到当前页的 `total/page_count` 后立即判断 `page > page_count`，命中时直接提示"共 N 页，已到最后一页"并返回，不再渲染上游重复返回的第一页内容；已有缓存仍会在请求前拦截。

5. **签到状态**：新增 `_parse_daily_info()`：
   - 连续天数：优先读 `oldStep`（HTML 客户端）；没有时从 `record` 签到日历按日期从今天（今天未签则昨天）往前逐日统计。
   - 今日是否已签：`error == 'finished'` 或当天日期在签到记录中。
   - `/jmcheckin` 签到成功后重新拉取一次状态；并写入本地 `checkin_state.json`，接口日历更新延迟时用当天记录兜底。
   - `/jmme` 额外显示活动进度 `currentProgress`。

## 2026-10-21 v0.7.3 超长单章分册与页段续传

### 一、问题与根因

1. **PDF 单章超限不切分**：原 `_plan_pdf_groups()` 只在当前册已有章节时才判断“当前页数 + 新章页数 > 上限”。一本书只有一章且该章 500/1000 页时，当前册为空，判断永远不触发，最终生成一个超大 PDF，QQ 发送容易超限，img2pdf 内存和打包耗时也明显上升。
2. **ZIP 只按章数合并**：`zip_group_size` 只限制章数，单章 1000 页或多章 5×150 页都可能生成数百 MB 的压缩包。
3. **限额提示无法精确续传**：旧提示只给章节范围（如 `-c 5`），续传会重新生成并重发第 5 章前面已经发过的分册。
4. **0 值没有语义**：`history_max`、`daily_file_limit`、`hourly_file_limit` 的滑杆最小值为 1，无法表达“保留所有历史 / 不限制文件数”。
5. **章节 ID 目标无法页段续传**：章节 ID 下载原来直接忽略 `-c`，限额中断后没有可用的续传入口。

### 二、修复方案

1. **引入页段模型 `PageUnit`**：以“章节内第 start~end 页”为打包最小单位。
   - 整章默认是一个页段；
   - 只有单章超过页数上限时才按上限切段（500 页 → 1-200、201-400、401-500）；
   - 超限章的最后一段允许和后续小章节合装，减少零碎文件。

2. **PDF 规划**：整章优先，按 `pdf_page_limit` 贪心装册；不再把超限单章整章硬塞进一册。
   - 50/30/150 页、上限 200 → 两册（50+30、150）；
   - 单章 500 页、上限 200 → 三册；
   - 500 页章 + 30 页章 → 第三册为 401-500 + 第 6 章 30 页。

3. **ZIP 规划**：新增 `zip_page_limit`（默认 300，`0` 表示只按章数），同时受 `zip_group_size` 章数和页数约束，先到哪个就封口。
   - 单章超限同样按页切分；
   - 多章 ZIP 的每个页段目录名也带 `_P起始-结束`；
   - `zip_page_limit=0` 时恢复为只按章数合并。

4. **页段解析与续传**：`-c` 支持 `章号:起始页-结束页`、`章号:起始页-`。
   - 页码从 1 开始；结束页省略表示到章末；
   - 结束页超过实际页数时夹取到章末并提示；
   - 起始页超过实际页数时忽略该章并提示；
   - 倒置页码（如 `400-201`）自动纠正并提示；
   - 整章与页段重复时整章优先，忽略页段；
   - 多个页段合并时取并集，任一段到章末则整体到章末。
   - 限额提示按剩余分组生成精确表达式，例如 `5:201-,6-8`、`5:401-,6`；
   - 章节 ID 目标使用 `p{id} -c 1:201-`，提示会自动带 `p` 前缀，避免被误判为整本重下。

5. **命名规则**：
   - 单章整章：`JM{章节id}_{漫画标题}_{章节标题}.pdf/.zip`；
   - 单章页段：`..._P201-400.pdf/.zip`；
   - 多章整章：`JM{漫画id}_{漫画标题}_{起始章}-{结束章}.pdf/.zip`；
   - 页段开头接后续章节：`..._005-006_P401-500.pdf/.zip`；
   - 多个页段同册时逐个标注章节号，例如 `..._004P401-500_005P201-300`，避免不同页码组合生成同名文件；
   - ZIP 内页段目录同样带 `_P起始-结束`。

6. **配置语义**：
   - `history_max=0` 保留所有历史；正数仍按原上限截断；
   - `daily_file_limit=0`、`hourly_file_limit=0` 不限制，帮助和状态显示“不限”；
   - `tease_enabled` 默认改为关闭；
   - 新增 `zip_page_limit`，默认 300，滑杆允许 0。

## 2026-10-21 v0.7.4 搜索/详情/下载稳定性修复

### 一、问题与根因

1. **搜索范围与超页**：`_render_search_page` 的 `start` 是 web 页内偏移，直接用于“第X-Y条”会从第 9 页起显示成 1-10；上游 API 对超大页码会夹到最后一页，原逻辑只判断空列表，导致 9999 页仍展示末页旧数据。
2. **章节 ID 当漫画 ID**：API 对章节 ID 返回畸形 album（`authors/tags=['filename']`、`name=*.zip`、章节列表为父漫画），`jmv`/`jmlist` 未校验就直接展示。
3. **评论边界**：`jmc` 未先验证漫画是否存在，无效 ID 返回 `page_count=0` 后走了“超页”分支；0 评论漫画也被 `1 > 0` 误判为超页。
4. **更新日期**：API 不提供 `update_date`，原代码固定输出“未知”。
5. **MAX_PATH**：jmcomic 默认用完整漫画/章节标题做目录名，长标题叠加后超过 Windows 260 上限，章节无法写入。
6. **CDN 502**：整本下载遇到部分图片失败直接抛异常，已下载的 800+ 张图片没有被打包发送；提示“已发送已完成部分”与实际行为不符。
7. **批量重复**：同一批次里漫画与其章节同时出现时，没有章节级去重，同一 PDF 被发送两次。
8. **不完整缓存**：只判断“漫画目录存在且有图片”就跳过整本下载，目录里只有一章时仍会打包出残缺 PDF。
9. **双扩展名**：章节名本身含 `.zip`/`.pdf`，`_safe_filename` 未去掉后缀，拼接输出扩展名后变成 `.zip.zip`/`.zip.pdf`。
10. **非连续命名**：多章文件统一用首尾章节号生成 `031-040`，实际只含 `31,35,40`。

### 二、修复方案

1. 搜索范围改用全局索引 `(qq_page - 1) * per_page`；先按 `total` 计算最大页数，超过直接提示，不再展示上游夹取的数据；0 结果统一使用“没有找到与「关键词」相关的漫画，请换个关键词试试”。
2. 新增 `_looks_like_chapter_album()`，在 `jmv`、`jmlist`、`jmc` 展示/请求前识别畸形 album，明确提示这是章节 ID 并给出 `/jm <id>` 下载入口。
3. `jmc` 先用 `get_album_detail` 校验漫画存在；`page_count == 0` 优先显示“还没有评论”，再做超页判断。
4. `jmv` 无 `update_date` 时回退 `pub_date`，两者都无则省略更新日期行。
5. 新增 `SafeDirRule(DirRule)`：仅当完整缓存路径超过 235 字符时截断目录组件，保留 `JM{id}_` / `P{id}_` 前缀；图片文件名预留 24 字符，避免超过 Windows MAX_PATH。
6. 整本下载增加 3 次重试；捕获 `PartialDownloadFailedException` / `RequestRetryAllFailException`，重试仍失败时使用已完成图片继续打包并提示缓存可续，不再整批作废。
7. 批次内记录已发送的 `(章节ID, 起止页)` 区间；后续目标若被完全覆盖则跳过并提示，避免重复文件。
8. 整本缓存改用 `_album_cache_complete()` 校验每个章节都有实际图片；不完整时只补下缺失章节/图片。
9. `_safe_filename()` 循环去掉 `.zip`/`.pdf`/`.rar`/`.7z` 等已知后缀，再清理非法字符。
10. 多章命名按实际章节号生成：连续用 `031-035`，非连续用 `031,035,040`；输出文件名整体去掉漫画标题。

## 四、BUG 状态汇总

### BUG-001（已修复，v0.7.6）jmv/jmlist/jmc 章节ID提示不含父漫画ID

- **状态**：✅ 已修复并验证（P49）
- **严重级别**：P2（影响章节ID目标的操作连续性，不崩溃）
- **环境**：v0.7.6 修复验证（API 客户端）
- **复现步骤**：`jmv 275013`、`jmlist 275013`、`jmc 275013`
- **实际结果**：提示只写 `/jmv <漫画id>`，未给出父漫画 ID
- **预期结果**：提示应包含“所属漫画：JM43164”和 `/jmv 43164`
- **根因**：畸形章节 album 的 `album_id` 等于输入的章节ID（275013），其章节列表首项的 `photo_id` 才是父漫画ID（43164）。原提示没有读取首项，也没有回退查询章节详情。
- **修复实现（v0.7.6）**：
  - 优先取畸形 album 首项的 `photo_id`；
  - 首项缺失时用 `get_photo_detail(章节ID).album_id` 兜底；
  - `jmv` / `jmlist` / `jmc` 三处提示都显示“所属漫画：JM父ID”，并给出 `/jmv 父ID`。
- **修复验证**：`275013` 首项 `photo_id=43164`，`1236387` 首项 `photo_id=1228973`，均能提取父漫画并触发章节ID提示；正常漫画 `43164`、`1228973`、`1484418`、`279092` 不误判为章节ID。

### BUG-002（已修复，v0.7.6）同章不连续页段被合并为连续范围

- **状态**：✅ 已修复并验证（P50/P51）
- **严重级别**：P2（导致未请求的页段被包含在输出文件中）
- **环境**：v0.7.6 修复验证（API 客户端）
- **复现步骤**：`jm 43164 -c 31:1-5,31:10-15`（第31章共19页）
- **实际结果**：日志显示共 15 页，PDF 包含第 6-9 页；ZIP 同样包含中间页
- **预期结果**：只包含请求的两段（1-5、10-15），共 11 页
- **根因**：`_select_chapters` 用 `page_ranges[value]` 只保存一个区间，重复出现同一章节时直接取 `min(start)` / `max(end)`；`_resume_expr` 对同一章节的剩余页段也取最小起点和最大终点，因此把中间缺口一起带回。
- **修复实现（v0.7.6）**：
  - 页段改为列表保存，新增 `_merge_page_ranges`：只合并重叠或相邻（间隔≤1）的区间，不连续区间保留为独立页段。
  - `_resume_expr` 使用同一合并规则，按章节输出多个页段，例如 `31:001-005,31:010-015`，续传不会再包含已发送区间或中间缺口。
  - 同一章节多个页段下载时按章节ID去重，只下载一次；同一章节打包仍使用 `JM章节ID_章节标题`，每个页段追加 `_P起始-结束`。
- **修复验证**：`31:1-5,31:10-15` 规划为两段共11页，不包含第6-9页；用实际缓存图片生成 PDF，确认11个图片页；续传只输出 `31:010-015`。

### BUG-003（已修复，v0.7.7）整本下载的进度推送从未生效（README 描述与实际不符）

- **状态**：✅ v0.7.7 已修复并本地验证（真实 QQ 待复测）
- **严重级别**：P2（文档承诺的功能实际不工作，影响下载体验；不崩溃、不影响文件产出）
- **环境**：问题发现于 v0.7.6；v0.7.7 修复验证（API 客户端、整本下载，不带 -c）
- **复现步骤**：`jm 1228973`（4章；测试时显示187页，v0.7.7 复验 API 返回185页，以实际为准；缓存不完整触发整本补下，实测下载约 6 分钟），观察聊天消息与 backend.log
- **实际结果**：全程只有"⬇️ 开始下载 → 📦 缓存不完整 → ⚠️ 第1次下载有图片失败…正在重试 → 开始打包PDF → 下载完成"，**没有任何"⏳ 下载进度：X%"消息**；日志中同样零进度记录（P36 测试 20:13-20:19 全程）
- **预期结果**：README"其他说明"承诺"整本下载时每 3 秒推送一次进度百分比"
- **根因（代码已确认）**：`ProgressDownloader.before_album`（main.py:43-53）用 `photo.page_arr` 累加 total；但 jmcomic 2.7.9 异步下载器在 before_album 钩子执行时各章 page_arr **尚未拉取**（`check_photo` 在之后才逐章执行，jm_async_downloader.py:135 vs :190），**total 恒为 0**；轮询循环的 yield 条件 `prog["total"] > 0`（main.py:1883）永不满足。旁证：jmv 能正确显示总页数是因为用的是 `album.page_count`（main.py:2618）而非章节 page_arr
- **证据**：main.py:43-53/1878-1887；jm_async_downloader.py:135/190；P36 测试日志时间窗
- **修复方向**：① before_album 改用 `album.page_count` 作为 total（jmv 已验证该字段可用）；② 或在 before_photo 中累加 total（check_photo 之后 page_arr 才有效）。另注意：选章/单章下载走 `_ensure_photo_downloaded` 路径本身无进度设计，如需全覆盖需另行补充
- **修复实现（v0.7.7）**：`ProgressDownloader.before_album` 改用 `album.page_count`；`before_photo` 记录当前章节序号和章节总数；轮询循环默认每约 10% 推送一次，并每 60 秒补发心跳；消息带 10 格进度条。新增 `progress_step` 配置（0=关闭，默认 10）。选章/单章路径未纳入进度推送，保持原行为
- **修复验证**：真实 API 确认 `album.page_count` 在 before_album 阶段可用（1228973 返回 185 页，章节 `page_arr` 此时仍为 0）；本地测试覆盖 total、章节序号、进度文案、10% 步进/心跳条件和进度条
- **推送策略设计（修复时一并落地）**：修好 total 后，去重逻辑不能沿用现在的"百分比每次变化都发"（快下载会每分钟蹦 20 条，比不发更糟）。采用**程序自动组合、不让用户选模式**的策略：
  - **主策略：百分比步进**——默认每 10% 发一条（10/20/…/90 共 9 条上限），消息数有界是聊天场景第一要素（对比插件 cosmos 同为 10% 步进方案）
  - **辅策略：时间心跳**——距上次进度消息超过 60 秒且仍在下载时，自动补发一条当前百分比；解决慢网络下纯百分比"装死"的问题（实测 CDN 限速 7 张/分钟时，卡在某个百分比可安静数分钟，用户无法区分"慢"和"挂"）
  - 两个机制取先触发者；纯时间方案在长下载下不可用（4862 页整本 20 分钟@3 秒≈400 条刷屏），纯百分比在慢速下静默，均不作可选模式
  - 用户侧最多一个开关：`progress_step`（百分比步进，0=关闭，默认 10），心跳间隔写死 60s 内部常量
  - 附带改进：多章整本下载带章节粒度（"⏳ 第3/4章 下载中 45%"，before_photo 钩子已具备条件）；进度条字符可并入同一条消息（如 `⏳ 45% [████░░░░░░] 第3/4章`），零额外消息成本
- **关联命令**：jm / jmzip 整本下载（选章、单章、缓存命中场景本就不涉及）
- **稳定性**：必现
- **补充说明**：ChatUI 只显示命令的最后一条消息，即使修复后在 ChatUI 也看不到进度（仅 QQ 群等逐条消息平台可见）；v0.7.7 已加入 10 格进度条，与进度消息同条发送，不额外增加消息数

### BUG-013（v0.7.8 已实现 A 版）QQ 官方单聊被动回复 4 次上限导致消息失败/降级

- **状态**：✅ v0.7.8 A 版已实现并本地测试通过（2026-10-23；真实环境待复测）
- **严重级别**：P1（一条命令超过 4 条消息就丢或延迟，直接影响核心体验）
- **环境**：QQ 官方机器人 C2C 单聊、AstrBot v4.28.2、插件 v0.7.8、`backend.log`
- **现象（实测日志，21:47:42 `jm 1215253 -c 31-37`）**：
  - 21:47:42.801 `⬇️ 开始下载 JM1215253…`（第 1 条）
  - 21:47:43.475 `📦 第31-37章已有缓存，跳过下载`（第 2 条）
  - 21:47:44.230 `开始打包PDF，共 191 页...`（第 3 条）
  - 21:47:45.270 `📤 打包完成：文件 29.5MB…`（第 4 条）
  - 21:47:45.925 `📎 JM1215253_031-035.pdf`（第 5 条）→ 超限
  - 之后每条都报 `ServerError: 回复消息失败，被动回复时间或者次数超过限制`（错误码 40034128），`tenacity` 2s/4s 重试仍失败
- **平台规则（QQ 官方文档）**：单聊被动回复 **60 分钟内有效、每条用户消息最多回复 4 次**；群聊 **5 分钟、5 次**
- **AstrBot 现行为**：被动失败后自动降级主动接口（`回复消息失败: …超过限制, 尝试使用主动发送接口。` → `使用主动发送接口发送成功。`）。消息通常不丢，但延迟 2~6 秒，并开始消耗主动额度
- **为什么不能“全部改走主动接口”（已否决）**：
  - 主动额度更小：官方一处写「单聊主动消息**每月 4 条**」，另一处是「20/qpm、每用户每天 1000 条」，按最保守口径撑不住
  - 用户可在 QQ 客户端关闭「允许主动发送」，关闭后主动消息一律失败，连正常回复都会失联
  - 全主动有被判营销/骚扰的限流、封禁风险
  - 实现上要改 AstrBot 库文件（`qqofficial_message_event.py:634-636` 去掉 `msg_id`），升级会被覆盖且无配置开关
- **已实测无效**：`provider_settings.buffer_intermediate_messages=true` 无改善。该开关只缓冲 Agent 多步工具调用中的 LLM 文本链（`astr_agent_run_util._should_buffer_llm_result` / `_merge_buffered_llm_chains`），插件 `@filter.command` 逐条 `yield` 的消息由 `respond/stage.py` 直接逐条发送，不在缓冲范围
- **改进方案（插件侧合并消息）**：
  - 消息 1：开始下载 + 缓存状态 + 开始打包（合并为一条）
  - 消息 2：文件（每个文件 1 条）
  - 消息 3：下载完成汇总（含限额状态）
  - 单文件命令 = 3 条，双文件 = 4 条，正好卡单聊上限；3 个以上文件靠“稍后继续”分批
  - 预算：**单聊 ≤4 条 / 60 分钟；群聊 ≤5 条 / 5 分钟**（群聊长任务超时后必须让用户再发一条刷新窗口）
- **附带建议**：`40034128` 属配额类错误，应标记为不可重试，免去每次 2s+4s 的无谓等待
- **A 版实现（2026-10-23）**：
  - `/jm`、`/jmzip` 只保留 1 条开始状态、每个文件 1 条和必要的失败/限额提示；移除逐章下载、缓存命中、开始打包、打包完成和重复进度消息；收尾汇总合并为一条，预算不足时省略
  - 按 QQ 官方预算计算：单聊 4 条、群聊 5 条；当“开始状态 + 文件数”已占满预算时省略收尾汇总，避免触发主动接口降级
  - 移除可见进度条、`_progress_bar` / `_progress_message` 和 `progress_step` 配置；保留 `ProgressDownloader` 内部状态
  - 新增 `/jmnow`：按发送者查询当前 JMID、已完成/总页数、未完成页数；没有任务时返回“当前还没有下载”
  - 新增 `/jmnext` 和“下一页/下页”自动翻页，仅做翻页，不做消息队列；会话有效期由 `page_turn_timeout` 控制（默认 60 秒，0 关闭）
  - `jmv` / `jmlist` 章节行追加每话页数，页数缺失时显示“页数未知”
  - 本次不实现 `/jmnext` 文件队列、自动补发或主动消息队列；文件数超过被动预算时仍保持现有降级行为，留待 B 版

### 9.7 话列表页数补齐（方案 2 + 缓存 + 后台预取，2026-10-23）

- **原因**：`/album` 的 `series` 每项只有 `id/name/sort`，`total_photos` 是整本总页数；每话页数只能从 `/chapter` 详情的 `page_arr` 取得。
- **实现**：
  - 新增配置 `page_prefetch_pages`：默认 2，范围 0-5，0=关闭；
  - `CatalogService.enrich_chapter_pages()` 只处理调用方传入的可见话：`jmv` 前 10 话、`jmlist` 当前页 10 话；
  - 当前页返回后，`schedule_page_prefetch()` 在后台继续预取之后 N 页（默认 2 页）；同一 album 只保留一个后台任务，重复 `jmv/jmlist` 不重复启动；
  - 前台/后台共用一个 `inflight[photo_id]` 任务表，同一话不会被重复请求；
  - 后台每 10 话合并写一次 `CacheService.update_album_page_counts()`，并用 `CacheService` 的进程内锁保护 metadata 读改写；
  - `CacheService.update_album_page_counts()` 把 `{photo_id: page_count}` 合并进 `downloads/JM{漫画id}/metadata.json` 的 `chapters`；
  - 后续查看先读 `CacheService.read_album_page_counts()`，全部命中时不再发请求；
  - 未下载过的漫画允许只创建 metadata、不创建图片目录，`find_album_dir()` 仍会因无图片而忽略它。
- **验证**：
  - `JM43164` 前 10 话首次补齐约 8.0 秒，第二次 0.004 秒且不调用 `get_photo_detail`；
  - `JM1215253` 前 10 话首次约 6.0 秒；后台预取 20 话约 11.8 秒（并发 3）；
  - 连续翻页实测：第2页 12.7 秒、第3页 5.5 秒、第4页 9.2 秒、第5页 8.2 秒；已缓存页约 1.5 秒；
  - 详情请求使用 `fetch_album=False, fetch_scramble_id=False`，避免每话额外拉整本详情和密钥；
  - `format_chapter_line()` 输出如 `第2话 [JM274971] 61（20页）`。
- **代价**：每个漫画第一次查看当前页会多最多 10 个详情请求；后台再按配置预取 N 页（默认 2 页，约 20 个请求）；之后走 metadata 缓存。
