## 一、审计方法与复核标准

### 1.1 第一性原理

不问“这段代码写得好不好”，而是回到问题本质：

- **这个插件为什么存在？** —— 把 JMComic 网站的漫画下载能力封装成 AstrBot 机器人命令。
- **它的核心约束是什么？** —— 上游 jmcomic 是黑盒且接口不稳定；QQ 平台有消息条数限制和内容审核；磁盘带宽有限；单用户并发不能无限。
- **哪些是必要的，哪些是过度设计？** —— 逐层剥离“因为一直都这样”的假设，找出真正的不变量和可以砍的复杂度。

### 1.2 对抗性审查

默认怀疑态度，主动尝试推翻代码的正确性假设：

- **破坏者视角**：这段代码在生产环境会怎么炸？极端输入下会怎样？
- **安全审计视角**：有没有越权、注入、信息泄露、资源滥用？
- **新员工视角**：新来的人能看懂吗？哪些地方藏着坑？
- **正确性视角**：逻辑真的对吗？边界条件呢？并发呢？

### 1.3 复核判定标准

| 结论 | 含义 | 处理方式 |
|---|---|---|
| **成立** | 代码事实与影响均可复现 | 进入修复清单 |
| **部分成立** | 事实存在，但机制、场景或定级有偏差 | 按复核后的级别处理 |
| **不成立** | 与代码或上游事实冲突 | 不修，保留结论避免重复审计 |
| **主观判断** | 设计取舍，不是可验证的缺陷 | 记录，不排期 |

原报告共 18 条发现（P0×3、P1×6、P2×5、P3×5）。复核后：

- 需要修复的硬缺陷：**3 条**（refresh_option、history 全量读写、订阅无退避）。
- 需要降级的：**6 条**。
- 证伪的：**3 条**（P0-3、P3-3、P3-4）。
- 主观判断：**2 条**（P2-3、P2-5）。

## 二、第一性原理拆解

### 2.1 这个插件的本质

剥掉所有功能描述后，这个插件只做三件事：

| 层 | 本质 | 依赖 |
|---|---|---|
| **输入层** | 把 QQ 消息解析成 `(目标ID, 章节选择, 输出格式)` | AstrBot 事件系统 |
| **执行层** | 调用 jmcomic 库下载图片到本地缓存目录 | jmcomic 库 |
| **输出层** | 把本地图片打包成 PDF/ZIP，通过 QQ 文件发出去 | AstrBot 消息组件 |

中间所有的服务（缓存、分页、限额、敏感词、签到、收藏、订阅）都是围绕这三件事的**状态管理**和**体验优化**。

### 2.2 核心不变量（真正不能动的东西）

1. **图片缓存是磁盘上的连续前缀** —— `00001.jpg, 00002.jpg, ...`，缺页会留洞。这是页段下载和续传的基础假设（`core/downloader.py` 的 `page_limit` + `services/cache.py` 的 `chapter_complete`）。
2. **登录态有时效** —— 实测约 30 分钟后收藏夹接口返回 401；插件默认 10 分钟主动重登，可由 `login_ttl_minutes` 调整（`core/client.py:14-17`）。
3. **QQ 官方被动消息有条数预算** —— 单聊 4 条、群聊 5 条。`services/messaging.py:55` 提供预算，`services/download_runner.py:487` 在预算不足时省略收尾汇总。
4. **上游 jmcomic 会变** —— 接口、类名、钩子签名都可能变，所以需要 `core/jmcompat.py` 兼容层与契约测试。

### 2.3 可以被质疑的假设

| 假设 | 复核意见 |
|---|---|
| “敏感词转拼音能绕过 QQ 审核” | 审核规则是黑盒，无法静态验证。这属于产品取舍，不是可修复缺陷。代码已支持 `custom_sensitive` 自定义表，方向是对的。 |
| “所有用户都可以下载” | 属实。下载命令只受 `allow_group` + 群白名单约束，不限 owner；但 `daily_file_limit` / `hourly_file_limit` 提供额度，**默认都是 0（不限）**，所以资源滥用风险成立。 |
| “内存状态不需要清理” | 属实但量级很小：`id_type_cache`、`page_sessions`、`_album_dirs` 都没有 TTL；单条占用几十到几百字节，长期运行是缓慢增长，不是 OOM。 |
| “线程锁能保护 asyncio 代码” | **归因错误**。这些锁的调用方都在事件循环线程，锁本身不竞争；真正的问题是锁内的同步磁盘 I/O。见 §4.2。 |

## 三、确认需要修复的问题

### 3.1 P1-A：`refresh_option()` 在 frozen dataclass 上必然失败（原 P2-4）

**位置**：`core/config.py:171`（`@dataclass(frozen=True)`）、`core/config.py:386-405`（`self.option = ...`）、`core/client.py:53-56`（吞掉异常）

**结论：成立，必现。**

`PluginSettings` 是 `frozen=True` 的 dataclass，`option` 是普通字段。`refresh_option()`
里直接 `self.option = _build_option(...)`，会触发 dataclass 生成的
`__setattr__`，抛出 `FrozenInstanceError`。

**复现**：

```python
from pathlib import Path
from astrbot_plugin_jmcomic.core.config import PluginSettings

settings = PluginSettings.from_config({}, Path("."))
settings.refresh_option()
# FrozenInstanceError: cannot assign to field 'option'
```

不是推测：v0.7.19 实测直接抛错。

**影响**：

- `JmClientManager._sync_generation()` 在检测到 jmcomic 模块换代时调用
  `settings.refresh_option()`，异常被 `try/except` 吞掉，只留一条 warning。
- 结果是：**option 从未真正重建**，旧代的 `JmOption` 继续被传给新代的
  `download_photo_async`。这正好落在 BUG-027 想修的“跨代类不匹配”路径上。
- 现有 `tests/test_client_generation.py` 用的是自带 `refresh_option()` 的
  `FakeSettings`，所以测试全过，掩盖了真实 dataclass 的问题。

**修复方向**：

```python
option = _build_option(...)
object.__setattr__(self, "option", option)  # 只更新运行期依赖句柄
return option
```

保留 `frozen=True` 对其他字段的只读约束，最小改动。补一个用**真实**
`PluginSettings` 的测试，断言 `refresh_option()` 不抛异常且返回新对象。

**复核后级别**：P1（正确性 / 潜在跨代故障）。

### 3.2 P1-B：history.json 全量同步读写，且默认无上限（原 P1-5）

**位置**：`services/history.py:39-48`（`add_user` 里 `load()` + `save()`）、
`services/history.py:26-33`（tmp + `os.replace` 全量写）、
`services/download_runner.py:456`（每发完一个目标写一次）、
`handlers/library.py:116/144/209`（`/jmhis` 读）、
`core/config.py:358`（`history_max` 默认 0）、`_conf_schema.json`（默认 0）

**结论：成立，且比原报告更严重。**

- `add_user()` 每次都把整个 `history.json` 读进来、插入一条、再整体写回。
- `history_max` 默认 **0 = 保留全部**，文件没有上限；用户越多、下载越多，文件越大。
- 这些调用都在 async 处理器/async generator 里同步执行，会直接阻塞事件循环。
- 原报告把它归因于 `threading.RLock` 竞争，不准确；锁在这里是必要的
  （转线程后尤其如此），真正的问题是**同步文件 I/O 跑在 loop 里**。

**修复方向**：

1. 读、写、追加全部通过 `asyncio.to_thread` 执行（`HistoryService` 提供
   `load_async` / `save_async` / `get_user_async` / `add_user_async` 包装）。
2. `history_max` 默认值改为 200（仍保留 0 = 不限的语义），把默认安装的文件
   规模限制在“用户数 × 200 条”。
3. 保留 `threading.RLock`：转线程后它才真正承担并发保护。

**复核后级别**：P1（性能 / 可靠性）。

### 3.3 P1-C：订阅检查失败永不退避（原 P1-4）

**位置**：`services/subscriptions.py:127-130`（失败只 warning）、
`services/subscriptions.py:134-146`（`loop` 固定间隔重试）、
`core/config.py:347`（`subscribe_interval` 默认 3600）

**结论：成立。**

- 某本漫画被删或持续 404 时，每个检查周期都会重新请求并写一条 warning。
- 没有失败计数、没有失效标记、没有退避。
- 100 本订阅里 10 本失效，按默认 1 小时周期，一年约 87600 次无效请求和日志。

**修复方向**：

- 在订阅记录里增加 `fails` 与 `next_check_at`。
- 失败时 `fails += 1`，退避 `interval × 2^min(fails,4)`，上限 24 小时。
- 成功取到详情后清零失败状态；退避信息随订阅文件持久化，重启后仍生效。
- 不永久标记失效，避免漫画恢复后订阅永远死掉。

**复核后级别**：P1（可靠性）。

## 四、证伪与降级项

### 4.1 P0-1：类变量全局共享 → 降为 P3

**原结论**：`_progress` / `_album_dirs` 并发串扰、长期运行 OOM。

**复核**：

- `core/downloader.py:169-171` 确实是类变量，`core/downloader.py:146` 的
  `_album_dirs` 从不清理，`_progress` 只在重下前 `pop`（`services/download.py:72`、
  `services/download_runner.py:203`）。这部分属实。
- 但 `before_album` 里 `dict[key] = {...}` 在 CPython 下是单条 `__setitem__`，
  GIL 保证原子，原报告“不是原子的”说法错误。
- 真正的竞态是 `state['done'] += 1`（`core/downloader.py:136`）这种读改写，
  只影响进度显示，不影响下载结果。
- `_album_dirs` 残留项在 `services/cache.py:47` 使用前会校验目录存在且含图片，
  陈旧映射不会误用。
- 1000 本漫画的残留约几百 KB，不会 OOM。

**结论**：部分成立，影响是“轻微内存增长 + 进度显示可能串”，P3。

---

### 4.2 P0-2：threading.RLock 阻塞整个机器人 → 降为 P2，并补充真正的阻塞点

**原结论**：RLock 在 asyncio 里同步使用，一个用户阻塞整个机器人。

**复核**：

- 三个锁：`services/cache.py:19`、`services/history.py:11`、`services/quota.py:14`。
- 所有调用方都在事件循环线程（如 `download_runner.py:332/438/456` 直接调用），
  **没有第二个线程持锁**，锁本身不会竞争，`RLock.acquire()` 只是极短的原子操作。
- 真正会卡 loop 的是锁内的同步 JSON 全量读写；其中 history 的问题最严重，
  已单列为 §3.2。
- 复核新增：`JmClientManager.get_client()` 是同步函数，17 处直接在协程里调用
  （`handlers/album.py:86`、`handlers/search.py:35` 等）。登录态过期时会在
  事件循环里同步执行登录网络请求。这是比 RLock 更直接的阻塞点，原报告漏了。

**结论**：机制归因错误；真实问题是同步 I/O 与同步登录，P2（history 部分升为 P1）。

---

### 4.3 P0-3：签到连续天数跨月算错 → 不成立，真实问题方向相反

**原结论**：`signed_days` 只存“几号”，10 月连续 31 天 + 11 月 2 日会算成 streak=2。

**复核**：

- 上游文档明确：API 的 `record` 是**当月**签到日历，日期形如 `"01"`；
  HTML 的 `dateArray` 也是“当月已签到的日期数组”，且 HTML 直接返回 `oldStep`
  （连续天数），走不到兜底逻辑。
  见 `JMComic-Crawler-Python/src/jmcomic/jm_client_interface.py:392-425`。
- 因此“10 月 1-31 日 + 11 月 2 日同时出现在 `signed_days`”这个输入不可能由
  接口产生，原报告的核心场景不成立。
- 真实缺陷方向相反：每月 1 号只看当月日历，会把跨月的连续天数**少算**成 1。
  这只影响展示，不影响签到本身。

**结论**：不成立（作为 P0）；真实问题是月初少算，P3，暂不修。

## 六、修复顺序建议

### 本轮（v0.7.20）

1. **P1-A** `refresh_option`：`object.__setattr__` + 真实 settings 测试。
2. **P1-B** history：`asyncio.to_thread` 包装 + `history_max` 默认 200。
3. **P1-C** 订阅：`fails` / `next_check_at` 指数退避，成功清零。

### 下个版本（backlog）

4. `get_client()` 异步化或统一在调用侧 `to_thread`（17 处，需单独回归）。
   **v0.7.21 已完成**：新增 `get_client_async()`，16 处调用点改为 await，并修复
   `services/download.py` 的嵌套求值问题。
5. `id_type_cache` / `page_sessions` 加简单上限或定期清理。
6. 关键路径裸 `except` 补 `logger.debug`。
7. `_tag_alias` 持久化。

### 不建议现在做

8. `config.py` 拆分：收益低于改动风险。
9. history 改 SQLite：需要数据迁移和 `/jmhis` 回归，等文件规模真的成为问题再说。
10. 签到改存完整日期：接口不返回跨月数据，收益极低。

## 七、做得好的地方（不能只挑刺）

1. **jmcompat 兼容层**：为应对 AstrBot 重载 jmcomic 模块，做了一代际检测和动态类
   创建。这是一个非常实际的工程问题，处理得很细致。
2. **原子写文件**：`metadata.json` / `history.json` / `subscriptions.json` /
   `send_limits.json` 都是 tmp + `os.replace`，不会写一半损坏。
3. **分页会话隔离**：按 `(umo, sender_id)` 隔离，不同群不同用户互不干扰，且带超时。
4. **页段下载设计**：只下载 `1..N` 的连续前缀，保证缓存的连续性；命名、
   完整性判定、页数夹取都围绕这个假设展开。
5. **大量兼容代码**：签到接口的 list/空 data 兼容、chapter album 的畸形数据检测、
   `allow_redirect=False` 的处理……说明作者踩过很多坑，而且每个坑都留了注释。

---

## 八、总结

复核后，这个插件没有原报告所说的三个 P0 级结构性问题。真正需要处理的是：

1. **`refresh_option` 在 frozen dataclass 上必然失败** —— 隐藏最深，正好影响
   跨代兼容路径（P1-A）。
2. **history.json 全量同步读写 + 默认无上限** —— 文件越大，事件循环被阻塞越久
   （P1-B）。
3. **订阅失败没有退避** —— 失效订阅会持续产生无效请求和日志（P1-C）。

原报告的方法论（第一性原理 + 四视角）是有效的，但部分结论停留在“读起来像问题”，
没有回到代码和上游文档验证，导致：

- 把“锁”当成阻塞源，漏掉了真正的同步 I/O 和同步登录；
- 把“几号”当成跨月 bug，实际上接口只返回当月；
- 把“总量很小”的内存状态定成 P0。

后续审计应保持一条硬规则：**每条结论必须给出可复现命令或上游文档位置，
否则只能标为“待验证”，不能进入修复清单。**
