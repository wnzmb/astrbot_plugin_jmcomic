### 1.3 Feature 即插即用机制说明（不建议接入，仅备了解）

库的 `jm_feature.py` 提供一行式导出：`download_album(id, option, extra=Feature.export_pdf)` 自动完成"下载+导出 PDF"，按任务上下文自动选择 after_album/after_photo 钩子并注入参数，支持 export_pdf/export_zip/export_long_img 及组合。

**对本插件不适用**：打包层是自研的（封面/回退/信息文件/页段命名均不在库插件能力内），接入 Feature 等于重写打包层。


## 二、五个可加提议详细评估

### 提议①：订阅更新推送（✅ v0.7.8 已实现）

- **作用**：订阅漫画 → 后台定期检查新章节 → 发现更新在订阅会话内推送通知
- **实际实现**：
  1. 数据层：`subscriptions.json`，按会话 `umo` 保存 `{album_id: {title, photo_ids, updated}}`
  2. 后台任务：插件 `initialize()` 启动定时协程，默认 3600 秒检查一次（`subscribe_interval`，0=关闭）；每本之间间隔 2 秒
  3. 命令只保留一个入口 `/jmsub`：
     - `/jmsub <漫画id>` 订阅或更新基线
     - `/jmsub list` 查看当前会话订阅
     - `/jmsub del <漫画id>` 取消订阅
  4. 快照对比使用 `photo_id` 集合，避免章节被删/重排造成误报；只推送通知，不自动下载
  5. 推送：`context.send_message(umo, ...)` 向订阅时的会话发送“《标题》新增 N 章”和章节列表
- **注意点**：QQ 官方机器人平台可能不支持主动推送，失败时只记录日志并在下轮重试；群/私聊按会话 `umo` 独立订阅

### 提议②：代理支持（✅ v0.7.7 已实现）

- **作用**：IP 被地区封锁/限流时，通过 HTTP/SOCKS5 代理访问站点（当前只能靠换域名，无逃生通道）
- **实现思路**：配置 `use_proxy`(bool) + `proxy_url`(str) → 在构建 jmcomic option 时映射到 `client.postman.meta_data.proxies`（库原生支持，cosmos 同款接法：config.py:240-246）。注意 cosmos 的做法是"未配置时显式设空代理以覆盖系统代理"，可借鉴避免环境变量干扰
- **实现状态**：v0.7.7 已落地。`use_proxy=false` 时显式传空 dict 直连；开启且填写 `proxy_url` 时 http/https 都走该代理；支持 `http://host:port`、`socks5://host:port`（SOCKS5 需 PySocks）
- **成本**：最低（一个配置项 + option 构建处几行）
- **注意点**：切换后需重载插件生效；帮助文本注明支持的格式（http://host:port、socks5://host:port）

### 提议③：群白名单（✅ v0.7.8 已实现）

- **作用**：比现有 allow_group 总开关粒度更细——只允许指定群使用
- **实际实现**：配置 `enabled_groups`（逗号分隔群号，空=全部）；`allow_group=false` 时所有群禁用，否则再按白名单过滤；所有命令入口统一调用 `_check_permission()`，私聊不受影响
- **注意点**：QQ 官方机器人事件的群标识字段由平台适配器提供；被拦截时提示“本群不在插件群白名单中”

### 提议④：jms 纯数字可配置按车号搜索（✅ v0.7.8 已实现）

- **作用**：`jms 123456`（纯数字）时可选直返漫画详情，省去用户再打一次 `/jmv`
- **实际实现**：配置 `numeric_search_as_album`（默认关闭）；开启后 `/jms <纯数字>` 直接复用 `/jmv` 的详情展示流程，带页码/排序参数时仍按普通搜索处理
- **注意点**：默认关闭，避免把“123”这类正常搜索词误判为车号

### 提议⑤：收藏夹导出（✅ v0.7.8 已实现，30 秒二次确认）

- **作用**：把账号收藏夹导出为 CSV 文件发送，用于备份/迁移
- **实际实现**：`/jmfav export [文件夹id]`（仅号主，无加密/无密码）→ 第一次输入只提示，30 秒内再次输入相同命令才执行 → 遍历收藏夹生成 `id,author,name` 三列 CSV → 作为文件消息发送，发送后删除临时文件
- **注意点**：大收藏夹分页读取、按 ID 去重；CSV 用 `utf-8-sig`，Windows Excel 可直接打开；不同文件夹的导出命令不能互相确认

## 七、审查核实与功能落地（2026-10-23）

### 7.1 话列表页数补齐（方案 2 + 缓存 + 后台预取，2026-10-23）

- **原因**：`/album` 的 `series` 每项只有 `id/name/sort`，`total_photos` 是整本总页数；每话页数只能从 `/chapter` 详情的 `page_arr` 取得。
- **实现**：
  - 新增配置 `page_prefetch_pages`：默认 2，范围 0-5，0=关闭；
  - `CatalogService.enrich_chapter_pages()` 只处理调用方传入的可见话：`jmv` 前 10 话、`jmlist` 当前页 10 话；
  - 当前页返回后，`schedule_page_prefetch()` 在后台继续预取之后 N 页（默认 2 页）；同一 album 只保留一个后台任务，重复 `jmv/jmlist` 不重复启动；
  - 前台/后台共用一个 `inflight[photo_id]` 任务表，同一话不会被重复请求；
  - 后台每 10 话合并写一次 `CacheService.update_album_page_counts()`，并用 `CacheService` 的进程内锁保护 metadata 读改写；
  - `CacheService.update_album_page_counts()` 把 `{photo_id: page_count}` 合并进 `downloads/JM{漫画id}/metadata.json` 的 `chapters`；
  - 后续查看先读 `CacheService.read_album_page_counts()`，全部命中时不再发请求；
  - 未下载过的漫画允许只创建 metadata、不创建图片目录，`find_album_dir()` 仍会因无图片而忽略它。
- **验证**：
  - `JM43164` 前 10 话首次补齐约 8.0 秒，第二次 0.004 秒且不调用 `get_photo_detail`；
  - `JM1215253` 前 10 话首次约 6.0 秒；后台预取 20 话约 11.8 秒（并发 3）；
  - 连续翻页实测：第2页 12.7 秒、第3页 5.5 秒、第4页 9.2 秒、第5页 8.2 秒；已缓存页约 1.5 秒；
  - 详情请求使用 `fetch_album=False, fetch_scramble_id=False`，避免每话额外拉整本详情和密钥；
  - `format_chapter_line()` 输出如 `第2话 [JM274971] 61（20页）`。
- **代价**：每个漫画第一次查看当前页会多最多 10 个详情请求；后台再按配置预取 N 页（默认 2 页，约 20 个请求）；之后走 metadata 缓存。

### 7.2 外部审查核实与落地（2026-10-23）

审查文档：`docs/精读分析与优化建议.md`（基线 `110c46c`；该文件已于 2026-10-30 合并进本文后删除，遗留项见「十」）。

| 项 | 核实结果 | 处理 |
|---|---|---|
| A1 登录锁未启用 | **属实**。`subscriptions.check_once()` 用 `asyncio.to_thread(self.client.get_client)`，订阅线程与命令协程可能同时进入登录；原 `_client_lock` 定义为 `None` 且从未使用 | 已改 `threading.RLock()` 覆盖缓存检查 + login + refresh/invalidate |
| A2 history/quota 非原子写 | **部分属实**。直接 `write_text` 确实可能写一半损坏；但单事件循环内这些同步方法不会交错，“并发下载丢更新”主要在多线程/多进程才成立 | 已加进程内 `RLock` + `tmp + os.replace` |
| A3 无 tests 目录 | 属实 | 已在 7.3 补 `tests/`（parsing/selection/text/quota/pagination/maintenance/download），19 项通过 |
| B1 ZIP 改 STORED | **结论不成立**。实测 45 张 JPG：7.43MB → deflate 6.83MB（省 8.1%），耗时 0.61s；STORED 0.07s 但 7.44MB。QQ 文件限额下体积更重要 | 保持 `ZIP_DEFLATED` |
| B2 img2pdf 全量 bytes | 属实 | 已改为 `outputstream=...`，2 页测试 PDF 正常，失败时回退旧写法 |
| B3 订阅串行 sleep 2s | 属实，但 2s 是有意防限流 | 暂不改；如需提速可做 3-5 路并发 |
| B4 简繁双搜串行 | 属实 | 暂不改；两次并发请求会增加站点压力 |
| C1 版本号硬编码 | 属实（main/help/metadata 共 4 处） | 暂不改；下一版本再统一 |
| C2 zips/exports 不清理 | **部分属实**。正常发送后 ZIP/CSV 都会 `unlink`，只有进程崩溃或发送异常时才可能残留 | 暂不改；可后续加启动清理 |
| C3 缓存无界 | 属实，但增长很慢 | 暂不改；可后续加容量/TTL |
| C4 封面每次重下 | 属实 | 暂不改；当前“发完即删”是有意的清理策略 |
| C5 run_download 过长 | 属实（约 380 行） | 暂不拆；行为冻结优先 |
| C6 普通失败也打全栈 | **不准确**。`MissingAlbumPhotoException`/`RequestRetryAllFailException`/`PartialDownloadFailedException`/取消分支都直接返回，没有 `exc_info`；只有未识别异常打全栈 | 不改 |
| C7 `/jmnow` album_hint 不准 | **不准确**。`handlers/download.py:54` 只在“整个 target 是纯数字”时填 hint，批量时为空；后续 `progress.update` 会写入实际 album_id，`/jmnow` 显示当前目标 | 不改 |
| D1 jmlist 固定 sleep 1.5s | 属实 | 暂不改；用于 QQ 静默违规兜底 |
| D2 敏感词逐 tag 正则 | 属实但收益小 | 不改 |

结论：本轮只落地 A1、A2、B2；B1 因实测体积差异明显而否决；C6/C7 的描述与代码不符，不按建议改。F1-F3 已在 7.3 落地，F4/F5 另行排期。

### 7.3 实用功能批次：F3 / F1 / F2 / A3（2026-10-23）

- **F3 `-latest N`**：
  - `/jm <漫画id> -latest 5`、`/jmzip <漫画id> -latest 5`；

  - 删除前先预览，30 秒内再次发送相同命令才执行；活动下载的 `JM` 目录自动跳过；
  - 不删除 `zips/`、`exports/`，正常发送后它们本来就会 unlink，异常残留可手动处理。

  - 并行探测最多 3 个配置/自动域名（5 秒超时），显示 HTTP 状态与耗时；
  - 检查代理配置和登录态（`get_daily`），不输出密码/cookie；
  - 仅管理员或号主可用。
- **A3 最小单元测试**：
  - 新增 `tests/`，使用标准库 `unittest`，覆盖 `parsing`、`selection`（含 latest）、`text`、`quota`、`pagination`、`maintenance`（metadata 保留）、`download`（页数完整性）；
