# astrbot_plugin_jmcomic 精读分析与优化建议

> 精读范围：全部 41 个 Python 源文件（main.py + core/7 + services/17 + handlers/9 + ui/1），`_conf_schema.json`，README / CHANGELOG / 开发文档 / 重构计划。
> 版本基线：v0.7.8（git main@110c46c）。本文只做分析与建议，不改动任何代码。

## 1. 精读结论：代码库心智模型

### 1.1 架构分层（已从 5103 行 main.py 成功拆分）

```
main.py（组装根 + 23 命令 + 1 正则，~320 行）
  ├── handlers/   命令域编排：account album download favorites library navigation search subscribe system
  │     └── services/   业务能力：access cache catalog checkin download download_runner favorites history
  │                       messaging packaging pagination progress quota search selection subscriptions text
  │                             └── core/   底层：config(PluginSettings) client(JmClientManager)
  │                                          state(PluginState) downloader(ProgressDownloader) models parsing
  └── ui/         纯文案：help.py
```

- 依赖方向单向无环：`main → handlers → services → core`，`ui` 独立，符合 REFACTOR_PLAN 约束。
- 状态单一来源：`PluginSettings`（frozen，只读配置快照）、`PluginState`（运行期共享）、`JmClientManager`（登录客户端缓存，600s TTL）、`ProgressDownloader._progress/_album_dirs`（类级下载进度，唯一允许的类级可变状态）。
- 命令覆盖：搜索（jms/jma/jmt/jmr/jmw）、详情（jmv/jmlist/jmc）、下载（jm/jmzip/jmphoto/jmnow/jmstop）、翻页（jmnext/下一页）、账号（jmcheckin/jmme/jmfav/jmwhoami）、其他（jmrank/jmhis/jmdomain/jmupdate/jmrand/jmsub/help）。

### 1.2 关键链路

| 链路 | 入口 → 处理 | 亮点 |
|---|---|---|
| 下载 | `/jm` → DownloadHandler → DownloadRunner.run_download | 目标识别（a/p 前缀+探测）、选章/页段（-c 5:201-400）、PDF/ZIP 分册规划、批次内已发页段去重、QQ 文件限额中断+续传表达式、消息预算收尾 |
| 搜索 | `/jms` → SearchHandler → SearchService.render_search_page | 简繁双搜+去重、QQ页↔Web页（80条）换算、敏感词脱敏值还原搜索、下一页命令动态生成 |
| 翻页 | remember 会话 → /jmnext 或"下一页" → PageEventProxy 复用命令 → dispatch | 按 (umo, sender) 隔离、60s 超时、末页 at_last_page 标记 |
| 订阅 | initialize → loop → check_once | photo_id 快照对比（抗删章/重排）、会话级推送、每本 2s 间隔防限流 |
| 账号 | /jmcheckin /jmfav → Checkin/FavoritesService | 401 检测→refresh_client 重登重试、签到 data 兼容 str/list/dict、CSV 导出 30s 二次确认 |

### 1.3 工程质量评价

**优点**
- 平台适配极深：QQ 官方被动消息 4/5 条预算、每日/每小时文件限额、消息内容违规检测（异常+日志双路）、封面转 PDF 规避图片审核。
- 防御式编码密集：mtime 对账、图片编号空洞检测、畸形章节 album 识别、旧目录自动迁移、三级 PDF 回退（img2pdf→reportlab→Pillow）。
- 异常统一翻译（`handle_exception`），用户提示友好、内部有完整堆栈。
- 24 个 BUG 全部闭环，文档（README/CHANGELOG/测试流程/开发文档/重构计划）与代码同步。

**主要短板（详见第 2 节）**：并发正确性（登录锁未启用、JSON 无锁非原子写）、打包性能（ZIP deflate 白耗 CPU、img2pdf 全量 bytes 驻内存）、零单元测试、若干工程细节（版本号硬编码、无界缓存、封面重复下载）。

## 2. 优化建议（按优先级）

### P0 正确性 —— 建议下个版本首批处理

| # | 位置 | 问题 | 建议 |
|---|---|---|---|
| A1 | `core/client.py:31` | `_client_lock` 定义了但**从未使用**（`get_client()` 无锁）。多协程并发首登时可能重复创建客户端、重复 login，登录态写入存在竞态 | 用 `asyncio.Lock` 包住「创建 + login」段；登录 TTL 刷新也纳入锁内。成本低、收益直接 |
| A2 | `services/history.py`、`services/quota.py` | JSON 读写均为 `load → modify → save`，无锁且直接 `write_text`（无 tmp+os.replace）。并发下载完成时可能丢更新；写一半崩溃会损坏文件 | 统一改为「进程内 `threading.Lock`（或 asyncio 锁）+ 原子写（tmp + os.replace）」，可复用 `subscriptions.save` 的既有模式 |
| A3 | 整个仓库 | **无 tests/ 目录**，重构后回归完全依赖手工测试流程（测试流程.md） | 按 REFACTOR_PLAN 附录 C 测试矩阵补最小单元测试骨架：`parsing`、`selection`（页段解析/分册）、`text`（敏感词/还原）、`quota`（限额计算）、`pagination`（会话/超时）。先覆盖纯函数，再逐步覆盖 handler |

### P1 性能 —— 小改动、大收益

| # | 位置 | 问题 | 建议 |
|---|---|---|---|
| B1 | `services/packaging.py:244` | ZIP 用 `ZIP_DEFLATED` 压缩 JPG。JPEG 已压缩，deflate 基本无收益却吃掉大量 CPU；200+ 页大 ZIP 打包明显变慢 | 改用 `zipfile.ZIP_STORED`（存文件时间可测，300 页 ZIP 打包时间可显著下降；体积差异 <1%） |
| B2 | `services/packaging.py:146` | `img2pdf.convert(...)` 返回完整 bytes 再 `write_bytes`，整个 PDF 常驻内存，大分册峰值内存高 | 用 img2pdf 写文件形式（`img2pdf.convert(*paths, output=...)` 或 converter 上下文管理器流式写出），避免整包驻留 |
| B3 | `services/subscriptions.py:64` | `check_once` 串行遍历订阅，每本之间 sleep 2s；订阅一多（如 50 本）单轮要 100s+，会长期占住任务 | 改成信号量限并发（如同时 3-5 本），仍保留每本小间隔防限流 |
| B4 | `services/search.py:94` | 简繁双搜是 `for` 串行两次请求 | `asyncio.gather` 并行两次搜索，再合并去重；搜索响应可快 ~1 倍 |

### P2 健壮性与工程细节

| # | 位置 | 问题 | 建议 |
|---|---|---|---|
| C1 | `main.py:40/132`、`ui/help.py:6`、`metadata.yaml` | 版本号 4 处硬编码，升级易漏改 | 单一来源：从 `metadata.yaml` 读取 version（`import yaml` 已有依赖），或定义 `__version__` 后 main/help 引用 |
| C2 | `core/config.py:317` | `_cleanup_expired_cache` 只清理 `download_base_dir`；`zips/`、`exports/` 不清理，长期残留临时文件 | 清理范围扩展到 zip_base_dir 与 exports，或提供命令 `/jmclean`（见 F1） |
| C3 | `core/state.py`、`services/text.py:10` | `id_type_cache` / `comment_page_cache` / `_tag_alias` 无界增长，长期运行内存缓慢上涨 | 加 TTL 或容量上限（简单 LRU / 时间戳清理），三者都是纯缓存，可容忍淘汰 |
| C4 | `handlers/album.py:203` | `/jmv` 每次重新下载封面（`cover_{id}.jpg` → PDF → 删）。高频查看同一本时重复请求 | 短 TTL 封面缓存（如 1 天，落盘 `data_dir/covers/`），发送后保留到 TTL 过期，配合 C2 清理 |
| C5 | `services/download_runner.py` | `run_download` 仍约 380 行，REFACTOR_PLAN 已预告第二轮拆分 | 拆成：目标规划（targets/chapters/groups）→ 单目标下载 → 分组打包发送 → 收尾汇总 4 个私有方法，行为不变 |
| C6 | `core/client.py:110` | `handle_exception` 对普通失败也 `exc_info=True` 打全栈，日志噪音偏大 | 只有未识别异常才打全栈；已知类型（404/网络重试）用 `logger.warning` 摘要即可 |
| C7 | `services/download_runner.py:54` | 批量目标时 `/jmnow` 的 `album_hint` 只取第一个纯数字 target，批量场景显示不准确 | 用第一个解析出的 album_id 作为 hint（resolve 后回填），或在提示中显示"批量下载中" |

### P3 体验细节

| # | 位置 | 问题 | 建议 |
|---|---|---|---|
| D1 | `handlers/album.py:336` | jmlist 发送后固定 `sleep(1.5)` 再查日志，每次响应多等 1.5s | 保留兜底检测，但可先返回文本再异步查日志（延迟提示），或仅在曾命中违规的平台启用 |
| D2 | `services/text.py:41` | 敏感词替换逐 tag 全量正则，长列表（如 80 条搜索页）略慢 | 可先拼接一次替换再切分，或对命中词预编译；收益小，可选 |

## 3. 实用功能建议（按价值/成本排序）

### 高价值 · 低成本 —— 建议随 v0.7.9 一起做

| # | 功能 | 价值 | 实现要点 | 成本 |
|---|---|---|---|---|
| F1 | `/jmclean` 手动清理缓存 + `/jmdisk` 磁盘占用统计 | 服务器/Windows 上缓存膨胀是刚需；当前只能等启动时清理 | 复用 `_cleanup_expired_cache` 逻辑；`/jmdisk` 遍历 download_base_dir/zips/exports 统计大小与目录数 | 低（纯本地，1 个 handler + 1 个 service） |
| F2 | `/jmtest` 连通性诊断 | 「连不上/401/慢」是第一大类求助，现在只能靠 /jmdomain 猜 | 一键测：配置域名逐个 GET 探活（超时 5s）、代理连通、登录态（调 get_daily），输出结构化结果 | 低 |
| F3 | `/jm <id> -latest N` 下载最新 N 话 | 追更党高频操作；现在要 `-c 总话数-N+1~总话数`，需先 /jmlist 数话数 | 在 `select_chapters` 前把 latest 展开为末尾 N 个章节下标 | 低（解析层小改） |
| F4 | 订阅自动下载开关 `subscribe_auto_download` | 订阅目前只推送；追更自动化可一键补全 | 配置布尔项 + 每会话开关；新话出现时若开启则静默调 DownloadRunner（复用缓存/限额） | 中低（复用下载链路） |
| F5 | `/jmretry` 失败目标一键重试 | 失败仅汇总提示，不持久化；重试要重新输入完整命令 | history.json 增加 failed 标记或独立 failed.json（user→failed list），/jmretry 读取后逐个重跑 | 低 |

### 中价值 · 中成本 —— 视使用场景决定

| # | 功能 | 价值 | 实现要点 | 成本 |
|---|---|---|---|---|
| F6 | 按用户限流（per-user 日/时限额，叠加全局） | 群聊场景防单用户刷爆全局额度 | quota 增加 per-user 维度，`record_file_send`/`file_quota` 按 user_id 分桶 | 中 |
| F7 | `/jmstat` 下载统计面板 | 号主想看到「下了多少、最大的是谁、标签分布」 | 从 history.json 聚合：总次数/总大小/单本最大/趋势；纯本地 | 低中 |
| F8 | 同用户下载任务队列 | 现在同用户多任务并发，容易打爆站点/触发限流 | DownloadHandler.consume 改为 per-user 串行（asyncio.Queue）或信号量 1-2 | 中 |
| F9 | 收藏夹重复清理 `/jmfav dedup` | 参考库 `delete_duplicated_files`（MD5 去重）思路，清理缓存重复图片 | 对 download_base_dir 内同名图片做 MD5 索引，提示可删项 | 中 |

### 暂缓 / 低优先级

| # | 功能 | 说明 |
|---|---|---|
| F10 | 订阅导入/导出 | 换群/换设备迁移订阅；场景较小 |
| F11 | 定时下载（配合 AstrBot cron） | 与 F4 自动下载重叠，可合并设计 |
| F12 | 拼音→中文搜索增强 | pypinyin 反查误伤率高，收益不确定 |
| F13 | 评论发表 | 内容审核风险高，与「QQ 违规规避」整体策略冲突，不建议 |
